## Context

See proposal.md - Why. Ships are currently generated by `build_ship_surface`
(procedural polygons) and thrust is a procedural flame drawn by
`effects.draw_flame`. `SpriteCache` pre-builds one ship surface and one glow
surface per player, and `Renderer._draw_ship` rotates the ship surface by the
simulation angle.

The final artwork is 1024x1024 JPEGs with a near-white background (channel
values ~253-255) and no alpha channel. The ship faces "up" in image space: the
top of the silhouette is the nose and the bottom carries the engine, with the
engines-on variants extending a bright exhaust flame below the hull. A plain
white colorkey cannot be used because the ship contains bright, near-white
highlights (silver panels and the flame core) that must be kept.

## Goals / Non-Goals

- Goal: ships are drawn from the authored artwork, at the ship's simulation
  size, with the image background removed.
- Goal: the "engines on" image replaces the procedural flame while thrusting,
  and "engines off" is used otherwise.
- Goal: both engine variants are prepared once (cached), so per-frame cost is a
  single rotate/blit as today.
- Goal: keep the soft glow halo and the existing per-player colour identity.
- Non-Goal: keep the procedural ship builder as a fallback path; the artwork
  replaces it.
- Non-Goal: change ship physics, radii, or collisions - visuals only.
- Non-Goal: re-author or re-colour the artwork; use the provided files as-is.

## Decisions

### Assets bundled inside the package
Move the four JPEGs into `space_war/assets/ships/` (e.g.
`blue_engines_off.jpeg`, `blue_engines_on.jpeg`, `red_engines_off.jpeg`,
`red_engines_on.jpeg`). Loading is resolved relative to the module
(`Path(__file__).parent / "assets" / "ships"`), so it works from any working
directory. Alternative considered: a top-level `assets/` next to `main.py` -
rejected because it is not bundled with the package and depends on the CWD.

### Background removal via border-connected flood fill
Because the background is near-white but the ship also contains near-white
highlights, a whole-image threshold would punch holes in the ship. Instead the
background is found with a flood fill: starting from every border pixel, walk
across pixels whose darkest channel is bright (>= ~232), and clear exactly those
connected pixels to alpha 0. Highlights inside the ship are not reachable from
the border across bright pixels, so they are preserved. The mask is computed on
a downscaled (256x256) copy for speed, then applied as an SRCALPHA cut-out.
Alternative considered: `set_colorkey((255, 255, 255))` - rejected because it
would erase the ship's silver highlights and the flame core. The JPEGs are kept
as-is (pygame loads them without extra dependencies).

### Pre-rotate to nose-forward, then reuse the existing rotation
Because the artwork faces up and the simulation uses angle 0 = +x, each loaded
image is rotated once so its nose points along +x, matching the old sprite
convention. `Renderer._draw_ship` then keeps its existing
`rotozoom(sprite, -degrees(ship.angle))` call unchanged. The exact pre-rotation
sign is verified by the existing rotate-visibly test plus a visual check.

### Sprites carry both engine states
`SpriteCache` gains, per player, an idle sprite and a thrusting sprite (in
addition to the glow). `build_ship_surface(config, player, thrusting=...)`
becomes the loader (or a sibling helper), loading, background-keying, scaling to
the ship's on-screen size, and pre-rotating. Scaling targets the configured ship
sprite size (derived from `ship_radius`, so the on-screen size stays consistent
with collisions). `Renderer._draw_ship` selects the thrusting sprite when the
player's thrust input is held and the idle sprite otherwise, and no longer calls
`effects.draw_flame`.

### Keep glow, drop the flame effect
The glow halo is unchanged and still drawn under the ship. `effects.draw_flame`
is no longer used by the renderer; it may be removed or left unused, but the
spec no longer requires a procedural flame.

## Risks / Trade-offs

- [JPEG artefacts around the silhouette leave a faint light fringe against the
  dark playfield] -> the threshold cuts background pixels clearly, and the glow
  halo masks residual edges; the threshold constant can be tuned if a fringe
  shows up.
- [A ship highlight connects to the border across bright pixels and is erased]
  -> highlights are enclosed by darker outlines in the artwork, so they are not
  reachable from the border; verified visually for all four images.
- [Pre-rotation sign wrong, ship points the wrong way] -> covered by a
  dedicated orientation assertion / visual check during implementation.
- [Sprite scaling wrong, ships no longer match their collision radius] -> scale
  is derived from `ship_radius` by a single configurable factor, and existing
  sprite-size tests assert the bounding size is at least the ship radius.
- [Tests that asserted procedural properties (player sprites differ by RGBA,
  flame drawn only while thrusting) now fail] -> tests are updated to assert the
  new behaviour: image-backed sprites, distinct per-player artwork, and an
  engines-on frame differing from the engines-off frame while thrusting.

## Migration Plan

Single change; no persisted state. Rollback is reverting the commit (the four
images return to the root and the procedural builder can be restored). No
follow-up migration needed.

## Open Questions

None blocking - the remaining unknowns (exact rotation sign, exact scale factor)
are tuning details verified during implementation and do not change the specs.
